Gemma 4 12B and e5-large-v2 on g7.2xlarge (compared with g6e.2xlarge)

Ray on EKS PoC · cluster ray-on-eks (us-west-2) · Ray 2.57 / vLLM 0.25.1 · g7.2xlarge measured Oct 8, 2026 (re-run, matches Oct 7 within ~2%) · g6e measured Oct 7, 2026

Summary and recommendation

Recommendation: standardise on g7.2xlarge. EC2 has advised that g6e capacity is constrained and is not expected to grow, while g7 quota can be provided in all regions. This PoC saw the same thing: g6e.2xlarge had no capacity in us-west-2a, 2b or 2c for several hours (spot and on-demand), while g7.2xlarge launched immediately in all three zones. The tests below show what moving from g6e.2xlarge to g7.2xlarge means for both models.

  • Gemma 4 12B QAT on g7.2xlarge: runs well and generates at the same speed as g6e.2xlarge (~67 tok/s per user), with the same response time for cached prompts (62 ms). Prompt processing is slower: first token takes 1.05s vs 0.63s for a new prompt, so throughput under load is 25% lower at 16 concurrent users (316 vs 420 tok/s).
  • e5-large-v2 on g7.2xlarge: same performance as g6e.2xlarge (19 ms per single input, ~610 embeddings/s). No trade-off for embeddings.
  • Cost (on-demand): g7.2xlarge is 12% more per hour ($2.52 vs $2.24). Per million output tokens at 16 users, Gemma costs $2.22 on g7.2xlarge vs $1.48 on g6e.2xlarge (+50%); e5 costs $1.15 vs $1.05 per million embeddings (+9%).
  • Closing the gap on g7.2xlarge:
    • Avoid recomputing prompts. g7's gap is in prompt processing, so caching pays off most there. Prefix caching already makes repeat prompts as fast as on g6e (62 ms). The tiered KV cache extends this beyond GPU memory: revisited long prompts ran at 1.8× the throughput of no tiering.
    • Scale out. About 1.35 g7.2xlarge per g6e.2xlarge matches throughput at 16 concurrent users; Karpenter adds replicas, and g7 capacity is available.
    • Size by concurrency. At lower concurrency the gap is smaller (13% at 4 users, 18% at 8 users).

Setup

  • LLM: google/gemma-4-12B-it-qat-w4a16-ct (QAT, W4A16), fp8 KV cache, 64K context, prefix caching on, one replica on one GPU. Weights loaded from S3.
  • Embeddings: intfloat/e5-large-v2 (335M, 1024-dim), vLLM pooling runner, fp16, OpenAI /v1/embeddings.
  • Serving: RayService (ray.serve.llm), CPU head on r6a.2xlarge, GPU worker pinned to the instance type by Karpenter. Clients ran inside the cluster (no port-forward noise).
  • Nodes: g7.2xlarge (RTX PRO 4500 Blackwell 32 GB, 8 vCPU, 32 GiB, on-demand $2.52/h) and g6e.2xlarge (L40S 48 GB, 8 vCPU, 64 GiB, on-demand $2.24/h). g6e.2xlarge had no capacity in us-west-2a/b/c (spot and on-demand) for several hours, so the g6e runs used g6e.4xlarge, which has the same single L40S GPU. All costs use on-demand prices.
  • Prompts: the same six files on both instance types (CRM-style case triage, summaries, account briefs, JSON extraction), 2,746–6,321 input tokens, 512 output tokens. They are synthetic; rerun with the customer's own prompts for final sizing.

Both nodes top out at ~590 embeddings/s with one replica: the limit is request handling (HTTP/JSON, tokenization) rather than the GPU, and a 335M model uses a small fraction of either GPU. g7.2xlarge is a like-for-like replacement for embeddings; add replicas for more throughput.

Tiered KV cache on g7.2xlarge

vLLM 0.25.1's native tiered offloading (OffloadingConnector + TieringOffloadingSpec) keeps KV blocks in three tiers: GPU memory → 8 GiB pinned CPU RAM → local NVMe (instance store). No LMCache or extra images were needed; it is set through kv_transfer_config in the RayService.

150 documents × ~7.5K tokens, 8 concurrentFirst pass TTFT p50Revisit TTFT p50First pass wall timeRevisit wall time
g7.2xlarge, no tiering5.43s5.44s273s274s
g7.2xlarge, tiered KV cache6.59s5.72s220s148s (1.8×)
  • How it helped: the documents (~1.2M tokens) are more than the GPU cache holds, so without tiering every revisit recomputes the whole prompt. With tiering, evicted prefixes were loaded back from CPU/NVMe instead: about 24 GB of KV was reloaded and about two thirds of the revisit prompt tokens (770K) came from cache instead of being recomputed, so the revisit pass completed in 148s instead of 274s without tiering: 1.8× the request throughput on the same GPU. Median TTFT stayed about the same (5.7s vs 5.4s): the gain is less recomputation, which frees the GPU for more requests.
  • Best fit: multi-turn chats, agents and RAG over a recurring document set, where the same long prefixes come back after the GPU cache has moved on.
  • Cost: offloaded KV for this model is ~80 KB per token (all layers), so on g7.2xlarge's 32 GiB host the CPU tier holds only ~100K tokens; the 440 GB NVMe tier does most of the work. The first pass was ~1s slower per request (TTFT) because blocks are also written out to CPU and disk.
  • Watch out: vLLM's disk tier has no size limit or eviction yet. In an early run it filled the NVMe and Kubernetes evicted the pod. Production needs a dedicated, size-managed volume and cleanup.

Observability

  • Every RayService ran with the KubeRay History Server collector (KubeRay 1.7.1); after the services were deleted, their Ray Dashboards (nodes, actors, Serve replicas, logs) still replay from S3.
  • Ray, vLLM (65 metric names) and GPU (DCGM) metrics flow through ADOT into Amazon Managed Prometheus, labelled per Ray cluster, for Amazon Managed Grafana dashboards (Ray Serve LLM, Ray default, NVIDIA DCGM).
  • No public endpoints: all services are ClusterIP and the benchmarks ran inside the cluster.

Notes

  • Single run per test (10–32 requests per prompt and test); differences under ~5% are within noise.
  • g7.2xlarge ran on spot (capacity was available in us-west-2a/b/c); spot vs on-demand does not change performance. g6e.2xlarge was capacity-constrained throughout.
  • Raw JSON artifacts: data-stacks/ray-on-eks/examples/gemma4-vllm-rayserve/benchmarks/results/.
